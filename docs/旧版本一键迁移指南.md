# v1.4.1：旧版本一键迁移指南

如果 v1.4.0 在 Ollama 的 `manifests-v2/.../bge-m3/latest` 报“迁移不接受链接目录或文件”，并已显示“已回退迁移”：用 v1.4.1 的程序文件更新原新版目录，保留 data/private/backups，再双击“一键迁移旧版本.cmd”，仍填原旧版目录即可。复制阶段失败的旧记录会归档，原备份保留；不要覆盖旧版目录。也可以直接解压 v1.4.1 到另一个空目录迁移。

v1.4.1 单独处理 Ollama 的 Linux 文件链接：在原镜像的临时容器里以只读方式读取旧模型目录，将指向该目录内部普通文件的链接复制为普通文件，不下载模型、不修改旧链接。目录链接、越界、断链和循环链接仍会拒绝；其他业务目录继续禁止链接。

适用于本项目此前的所有版本：v1.0.0、v1.1.0、v1.2.0、v1.2.1、v1.3.0、v1.3.1。按实际部署结构识别，没有 VERSION 文件但仍是早期标准目录的部署也能识别。以后仍沿用这套目录结构的版本可再次迁移；这不等于承诺任意第三方改版、外置数据库或未知结构都可以自动搬运。

目的：让同一个 QQ 机器人换到新版部署器，保留原来的配置和记忆。你只输入一次旧版目录，不需要重新填写 QQ、Key、人设或手动挑选数据库。

## 一、先理解迁移后会发生什么

| 项目 | 迁移后的结果 |
|---|---|
| 主人 QQ、机器人 QQ、群白名单 | 原样保留 |
| 模型、接口地址、API Key、独立搜索 Key、代理设置 | 原样保留，不替换成新版默认值 |
| 人设、自定义提示词、会话配置 | 完整复制原数据库与配置文件 |
| 历史聊天、会话、最近流水 | 随整个 AstrBot 数据目录复制 |
| 长期记忆 | 连同插件数据库、向量索引、缓存、会话和反思状态一起复制 |
| 主动陪伴时间、签到、插件开关和自定义插件 | 保留旧插件代码与配置、全部本地插件数据 |
| 公开/私人表情库和选择配置 | 原样复制，不重新安装或改变选择 |
| QQ 登录数据、NapCat Token、OneBot 连接密钥 | 原样复制；是否免扫码由 QQ 服务决定 |
| Ollama 模型 | 完整复制本地模型和清单，不重新生成记忆向量 |
| 面板地址、端口、账号和密码 | 沿用旧配置，迁移成功后用原地址打开 |
| AstrBot/NapCat/Ollama 运行版本 | 继承旧的本地镜像 ID，不拉取 latest、不自动升级依赖 |
| 旧目录 | 保留所有原文件；切换时停止旧容器并关闭它们的自动重启 |
| 新容器与网络 | 使用新目录的独立名称，数据挂载指向新版目录 |
| Docker 程序和虚拟磁盘 | 继续复用原 Docker，不复制 data/docker-desktop 或重装 Docker |

这里升级的是部署包和管理入口。为了保持原有行为，迁移不运行“导入初始配置”“升级陪伴配置”“导入内置表情库”“配置 DS 联网搜索”，也不会给早期版本自动启用后来新增的插件。

逐文件相同意味着搬运前的配置和记忆没有被脚本重写，不代表大模型每次都生成一样的回复。云端模型更新、QQ 风控和网络状态仍可能影响体验；实际聊天及旧记忆召回需要最后检查。

## 二、开始前准备

1. 找到旧版部署包的根目录。应能同时看到 Deploy.ps1、compose.yaml、data 和 private，而不是只选 data 文件夹。
2. 把 **v1.4.0 新包解压到另一个固定的空目录**。例如旧目录为 `D:\Bots\旧版`，新目录为 `D:\Bots\新版`。两个目录不能相同，也不能互相包含。
3. 打开原来使用的 Docker Desktop，等待引擎运行。无需安装第二套 Docker，也不要迁移虚拟磁盘。
4. 新目录不要先“导入初始配置”，不要放入另一个机器人的数据。已有业务数据、容器或 Docker 虚拟磁盘的新目录会被拒绝；这是为了防止覆盖另一个机器人。
5. 确保磁盘有空间容纳 **旧业务数据约两倍的额外副本**：一份一致快照，一份新版运行数据，包含本地 Ollama 模型。旧文件、已有备份和 Docker 镜像仍占原空间。
6. 留出停机时间。复制较大的 QQ 文件和模型时，QQ 暂时离线是正常现象。迁移中不要手动启动旧入口，不要关闭窗口或 Docker。

可以先自行保留一份旧目录的离线备份。迁移入口本身也会保存完整业务快照；快照不含 Docker 虚拟磁盘，所以不能代替 Docker 引擎的整盘备份。

## 三、只输入旧目录，执行迁移

1. 进入 **新版目录**，双击 `一键迁移旧版本.cmd`。
2. 按提示粘贴旧目录的完整路径，例如 `D:\Bots\旧版`，回车。路径含空格、中文或外层双引号都可以。
3. 等待窗口完成。脚本将依次：
   - 检查旧结构、Docker 引擎、镜像、容器归属、数据挂载和面板端口；
   - 记录旧容器原来的运行状态和重启策略；
   - 停止旧服务，防止 SQLite、向量索引和 QQ 文件在复制过程中继续变化；
   - 复制全部本地业务数据与 private，跳过 Docker 虚拟磁盘；
   - 对源文件与副本逐个计算 SHA-256，并再核对快照到新版的复制；
   - 生成属于新版目录的实例身份和 Compose 配置；
   - 继承旧镜像、端口、DNS 和业务配置，启动新版并检查面板与本地向量服务；
   - 保存迁移记录，关闭旧容器自动重启，避免重启电脑后两份机器人抢同一个 QQ。
4. 看到“迁移完成”后，再做下一节的检查。以后只从 **新版目录** 使用一键启动、停止、备份和 DNS 修复入口。

高级用法：在新版目录打开 PowerShell，执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Deploy.ps1 -Action Migrate -SourceDirectory "D:\Bots\旧版"
```

用户电脑不需要安装 Python；迁移使用 Windows PowerShell 和原有 Docker。

## 四、迁移完成后的检查

先确认面板，再确认实际使用：

1. 打开 `private/本实例面板地址.txt`。地址应沿用旧版；用原来的 AstrBot 密码和 NapCat Token 登录。
2. 确认 NapCat 的 QQ 账号和 OneBot 连接状态。如果 QQ 要求重新扫码，就用原来的机器人 QQ 扫码；脚本不会删除登录数据，但无法阻止腾讯要求重新认证。
3. 在 AstrBot 中检查原来的模型、接口、搜索设置、人设和插件开关。不要点击重置或导入初始配置。
4. 查看历史会话，以及 LivingMemory 管理页中的旧记忆条目、会话归属和向量索引状态。插件名称因早期版本不同而可能不同，原来没安装的插件不会凭空出现。
5. 用原来的主人 QQ 发一条普通消息，再询问一条此前确实存储过的事实，例如原来记录过的饮食偏好。核对原模型回复、记忆召回、表情库和主动时段。
6. 测试满意后继续使用新版。旧目录和 `backups/migration-*` 暂时不要删除。

面板打开、文件摘要一致和容器运行都不能单独证明 QQ 已成功登录、模型请求成功或旧记忆实际被召回。

## 五、迁移记录在哪里

新版目录中会生成：

```text
migration.json                       本次迁移的状态和回退位置
compose.migrated.json                 已解析并改为新版挂载的旧运行配置
compose.lock.json                     本次继承的运行镜像
private/instance.json                 新版目录身份，保留旧面板端口
private/build-state.json              标明 adopted/migrated runtime 来源
backups/migration-日期时间/
  state.json                         旧目录、容器、原重启策略和迁移状态
  files.json                         每个快照文件的大小与 SHA-256
  source-compose.json                旧部署解析后的原配置
  source-snapshot/data/               旧业务数据的一致副本
  source-snapshot/private/            旧凭据、设置与实例信息的原始副本
  target-before/                     新目录迁移前的少量管理文件
```

迁移记录和副本可能包含 Key、Token、QQ 登录数据、聊天与私人记忆，和原 data/private 一样需要保密。不要把它们发到 issue 或上传公开仓库。正式发行包不包含这些内容。

## 六、失败或不满意时，一键回退

正常迁移发生错误时，会自动停止新版并尝试恢复旧容器原来的重启策略和运行状态。旧数据文件始终保留。如果意外关闭窗口、断电，或你检查后决定返回旧版：

1. 保留旧目录与新版目录，不要移动或删除迁移备份。
2. 打开原来使用的 Docker Desktop。
3. 在 **新版目录** 双击 `回退版本迁移.cmd`。
4. 等待“已回退迁移”，再打开旧版面板确认。

回退会停止新版容器、关闭它们的自动重启，并恢复迁移前原本正在运行的旧容器。原本停止的旧服务仍保持停止。重复点击已完成的回退不会再次搬动数据。

如果新版已经产生新聊天或新记忆，回退会将新版副本保存在 `backups/migration-日期时间/new-version-retained/`，避免丢弃它们；**不会把两套数据库自动合并**。旧版从迁移前的状态继续运行。复制阶段失败且已成功回退的情况，更新到 v1.4.1 后可直接重试，旧记录会归档；已经完成切换的情况要再次迁移，请使用新的空目录。

自动回退也可能因 Docker 不可用、文件占用或磁盘问题失败。窗口会明确提示未完成；此时不要同时启动两套机器人，先恢复 Docker/磁盘状态，再运行回退入口。若目录被手动修改导致回退冲突，保留全部文件和 state.json 后检查，不强行覆盖。

## 七、常见问题

### 旧版是 v1.0，没有实例设置，也可以吗？

可以。脚本识别早期固定项目 dsdeploy 和标准 data/private 布局，同时核对 Docker 标签的实际工作目录。v1.3 之后按旧实例身份定位。不会因为另一目录也存在一个 dsdeploy 就随便停止它。

### 为什么要求旧镜像仍在本机？

为了继承原来的运行环境，脚本从旧容器或本地镜像获得不可变 ID，而不是下载一个可能已改变的 latest。缺少旧镜像时，在停止旧服务之前报错。先恢复原镜像或在旧目录恢复正常运行，再迁移；不要为了“迁成功”偷偷换掉运行版本。

### 为什么不复制旧版整个 runtime 或 data/docker-desktop？

它们是安装器、缓存与 Docker 引擎存储，不是机器人专属的记忆目录。复制正在使用的虚拟磁盘不能保证一致性，也会影响其他项目。本脚本复用原引擎，完整复制业务 data（仅排除 docker-desktop）、private 和模型文件。

### 修改过插件、表情包或人设，能保留吗？

可以，只要仍保存在标准业务目录内。未知插件的数据文件也随整个目录复制，不只挑选内置插件；自定义插件代码也保留。云端数据库只保留原连接配置，不会把云端内容另行导出到本地。

### 自定义了 Compose、额外服务、外部挂载或符号链接怎么办？

脚本会检查并明确拒绝无法保证完整的情况，包括额外服务、外部数据卷、目录外挂载、固定容器名、外部网络、Compose secrets/configs 和目录链接。标准历史发行版不需要这些设置。拒绝表示没有宣称迁移成功；需要先核对自定义存储范围，不能把未知数据库漏掉后继续上线。

### 迁移会自动安装新版功能吗？

不会。v1.0 没有的表情或搜索能力不会被自动启用。迁移后仍可以按需要运行对应入口，但那属于另一项配置变更，运行前会单独备份。不要把“完全保留旧行为”和“自动开启全部新功能”混在一次操作里。

### 迁移后能不能删除旧目录？

暂时不要。回退需要原容器和原目录；原 Docker 安装位置、Docker 客户端上下文证书或虚拟磁盘还可能放在旧目录里。确认长期稳定并制定单独的引擎/备份迁移计划后再处理，不要把旧目录一键删掉。

## 八、本版验证范围

`tests/verify_migration.py` 在真实 Windows PowerShell 5.1 中运行迁移入口，用模拟 Docker 和合成数据覆盖六个历史版本布局，核对配置、SQLite 记忆、FAISS 索引、插件代码、QQ 会话文件、Ollama 模型的逐字节保存，以及原端口、镜像和 DNS 的继承。覆盖失败自动回退、回退保留新版新增数据、重复操作和错误容器归属/外部挂载/缺失镜像/链接拒绝。

这些是迁移流程和数据保存的回归验证，不是六套真实账号的 QQ 登录或付费模型/长期记忆召回验收。实际结果按第四节检查。

## 九、单独修复 NapCat DNS

迁移会保留旧 DNS，不会自动改网络。如果旧版已经存在二维码不刷新、卡在登录前阶段的问题，可在迁移和回退均已完成、实例能正常管理后，在新版双击 `修复NapCat DNS.cmd`。它备份原有专用 DNS 配置，为本实例 NapCat 设置 223.5.5.5 与 119.29.29.29，并只重新创建 NapCat 容器；QQ 会短暂断开。

要撤销，双击 `恢复NapCat DNS.cmd`。它不改系统 DNS，也不会清空 QQ 登录目录。DNS 配置成功不代表网络/防火墙问题或 QQ 登录已经解决；没有容器的目录会提示先完成部署。
